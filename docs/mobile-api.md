# DeviceTelemetry — API для мобильного приложения

Версия контракта: **1.1.0** (MVP). Машиночитаемая спецификация: [`mobile-api.openapi.json`](mobile-api.openapi.json) (OpenAPI 3.1, подходит для генерации клиента, см. [раздел 11](#11-генерация-клиента)).

API даёт четыре экрана: список устройств клиента, карточку устройства, его текущее состояние и историю событий. Все операции — только чтение (`GET`).

> **Временно без авторизации.** Endpoint-ы открыты всем, кто может достучаться до сервера. `customerId` и `deviceId` в URL не проверяются на принадлежность пользователю. Не публикуйте приложение в сторах с этой версией API: до production-запуска будет добавлена аутентификация, и контракт изменится (см. [раздел 12](#12-что-изменится)).

---

## 1. Подключение

| | |
|---|---|
| Базовый URL (Staging) | `http://<адрес VPS>:8080`, точный адрес уточните у бэкенд-команды |
| Префикс | `/api/mobile` |
| Протокол | Staging — HTTP; production — только HTTPS |
| Формат | JSON, UTF-8 |
| Методы | только `GET`, тела запросов нет |
| Аутентификация | нет (временно) |

**Staging работает по HTTP**, а мобильные ОС по умолчанию блокируют HTTP-трафик:

- **iOS:** App Transport Security. Для отладочной сборки добавьте исключение для домена или IP staging-сервера в `Info.plist` (`NSAppTransportSecurity` → `NSExceptionDomains`). В релизную сборку исключение не включайте.
- **Android 9+:** cleartext запрещён. Разрешите его только для staging-хоста через `network_security_config.xml` в debug-варианте.

CORS не настроен: нативным клиентам он не нужен, но веб-сборки (Flutter Web, React Native Web) запросы выполнить не смогут.

## 2. Общие соглашения

- **Имена полей** — camelCase. Набор полей фиксирован; при появлении новых полей клиент должен их игнорировать.
- **`null` отправляется явно.** Поля, отмеченные как nullable, всегда присутствуют в ответе со значением `null`, а не пропадают.
- **Идентификаторы:**

  | Поле | Тип | Пример | Что это |
  |---|---|---|---|
  | `customerId`, `id` клиента | целое (int32) | `1` | внутренний id клиента |
  | `deviceId`, `id` устройства | целое (int32) | `15` | внутренний id устройства, используется в URL |
  | `deviceCode` | строка, до 100 символов | `stg-device-001` | внешний код, которым устройство себя называет; для URL не используется |
  | `id` события | строка, UUID | `01a1455b-94b5-70f3-aa9c-7a54c081237d` | id события |

- **Время** — ISO 8601 в UTC, всегда с суффиксом `Z`. **Дробная часть секунд необязательна и бывает разной длины, от 0 до 7 знаков:**

  ```
  2026-10-16T10:05:00Z
  2026-10-16T15:36:32.18105Z
  2026-10-16T15:36:32.1234567Z
  ```

  Парсер должен принимать все три варианта. На iOS `ISO8601DateFormatter` с опцией `.withFractionalSeconds` не разбирает строки без дробной части, а без этой опции — строки с ней. Делайте две попытки разбора: с дробной частью и без. На Android `java.time.Instant.parse()` принимает все варианты.
  Показывайте время в часовом поясе пользователя.

- **Числа** передаются как JSON-числа, не строками.

## 3. Ошибки

Все ошибки возвращаются в формате [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457) с `Content-Type: application/problem+json`:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.5",
  "title": "Not Found",
  "status": 404,
  "detail": "The customer does not exist.",
  "traceId": "00-01d7076bba66388eb42aa77112f36844-af763bf2b95ca5f7-00",
  "code": "customer.not_found"
}
```

- **`code`** — стабильный машиночитаемый код. Логику клиента стройте на нём (и на HTTP-статусе), а не на тексте `detail`.
- **`detail`** — текст на английском для логов и отладки; пользователю его не показывайте.
- **`traceId`** — передавайте его в отчётах об ошибках, по нему бэкенд найдёт запрос в логах.

**Ошибки валидации запроса** — частный случай с другой формой. Если параметр нельзя разобрать (например, `deviceId=abc` или `limit=abc`), приходит 400 **без `code`**, но с полем `errors`:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": { "limit": ["The value 'abc' is not valid."] },
  "traceId": "00-971d0d3a8780eef4b639586f6109a74f-b9cc55408db01fd8-00"
}
```

При корректной работе клиента такая ошибка не возникает: она означает ошибку в коде формирования запроса.

### Коды ошибок

| HTTP | `code` | Когда | Что делать клиенту |
|---|---|---|---|
| 400 | `pagination.invalid_limit` | `limit` вне диапазона 1–100 | ошибка в коде клиента |
| 400 | `pagination.invalid_cursor` | `cursor` не получен от этого endpoint-а или повреждён | начать историю с первой страницы |
| 400 | — (есть `errors`) | параметр не разбирается | ошибка в коде клиента |
| 404 | `customer.not_found` | клиента нет | показать «не найдено» |
| 404 | `device.not_found` | устройства нет (например, удалено) | закрыть экран устройства, обновить список |
| 429 | `rate_limit.exceeded` | превышен лимит запросов | повторить через `Retry-After` секунд |
| 503 | `service.unavailable` | временно недоступна база данных | повторить через `Retry-After` секунд |
| 500 | — | непредвиденная ошибка сервера | повторить с нарастающей задержкой, затем показать ошибку |

Все запросы — `GET`, поэтому повторять их безопасно.

## 4. Лимит запросов

- **120 запросов в минуту с одного IP-адреса**, фиксированное окно в 1 минуту.
- При превышении приходит `429` с заголовком `Retry-After`: число секунд до сброса окна.
- Лимит считается **по IP, а не по пользователю.** Пользователи за одним NAT мобильного оператора или в одной Wi-Fi-сети делят общий лимит. Не делайте фоновых опросов чаще необходимого и не запрашивайте карточки всех устройств подряд при открытии списка.

## 5. Список устройств клиента

```http
GET /api/mobile/customers/{customerId}/devices
```

Возвращает все устройства клиента. Сортировка — по `name`, при равных именах по `id`. **Пагинации нет:** устройства заводятся вручную, у клиента их немного.

| Параметр | Где | Тип | Обязательный | Описание |
|---|---|---|---|---|
| `customerId` | путь | integer | да | id клиента |

**Ответ `200 OK`** — массив; если у клиента нет устройств, массив пустой.

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer | id устройства, используется в остальных запросах |
| `deviceCode` | string | внешний код устройства (можно показывать как серийный номер) |
| `name` | string | отображаемое имя, до 200 символов |
| `lastSeenAtUtc` | string (date-time) или `null` | **главное поле списка**: когда сервер в последний раз получил сообщение от устройства (по часам сервера). `null` — устройство ещё ни разу не выходило на связь |
| `silentSinceUtc` | string (date-time) или `null` | не `null`, пока сервер считает устройство молчащим (см. [«Жив ли прибор»](#жив-ли-прибор)) |

```http
GET /api/mobile/customers/1/devices
```
```json
[
  { "id": 1, "deviceCode": "stg-device-001", "name": "Staging Sensor 001",
    "lastSeenAtUtc": "2026-10-19T12:22:11.692209Z", "silentSinceUtc": null },
  { "id": 2, "deviceCode": "stg-device-011", "name": "Staging Sensor 011",
    "lastSeenAtUtc": null, "silentSinceUtc": null }
]
```

Показывайте в списке **возраст последнего контакта** («5 мин назад»), считая его от `lastSeenAtUtc` по часам телефона, и отметку о молчании. Только эти поля отвечают на вопрос «прибор жив?».

**Ошибки:** `404 customer.not_found`, `400` (нечисловой `customerId`), `429`, `503`.

## 6. Карточка устройства

```http
GET /api/mobile/devices/{deviceId}
```

| Параметр | Где | Тип | Обязательный | Описание |
|---|---|---|---|---|
| `deviceId` | путь | integer | да | `id` из списка устройств (не `deviceCode`) |

**Ответ `200 OK`:**

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer | id устройства |
| `deviceCode` | string | внешний код |
| `name` | string | имя |
| `customerId` | integer | id клиента-владельца |
| `lastEventAtUtc` | string (date-time) или `null` | время последнего события по часам устройства; `null`, если событий нет |
| `lastStatusCode` | integer или `null` | код статуса этого события; `null`, если событий нет |
| `lastSeenAtUtc` | string (date-time) или `null` | последний контакт по часам сервера (как в списке) |
| `reportIntervalS` | integer или `null` | период регулярного отчёта, который сообщил прибор; `null` — прибор его не сообщает и на молчание не контролируется |
| `silentSinceUtc` | string (date-time) или `null` | как в списке |

```http
GET /api/mobile/devices/1
```
```json
{
  "id": 1,
  "deviceCode": "stg-device-001",
  "name": "Staging Sensor 001",
  "customerId": 1,
  "lastEventAtUtc": "2026-10-16T10:05:00Z",
  "lastStatusCode": 200,
  "lastSeenAtUtc": "2026-10-19T12:22:11.692209Z",
  "reportIntervalS": 300,
  "silentSinceUtc": null
}
```

`lastEventAtUtc`/`lastStatusCode` — **последнее событие любого типа**, а не текущее состояние. Подписывайте его как «последнее событие» с датой. Последнее событие выбирается по времени устройства: событие, которое прибор накопил без связи и отправил позже, карточку не изменит. Текущее состояние — в [разделе 7](#7-состояние-устройства).

### Жив ли прибор

- **`silentSinceUtc` не `null`** — прибор **не выходит на связь**: сервер не получил от него ни одного сообщения дольше `max(3 × reportIntervalS, 10 минут)`. Так и показывайте, с датой.
- **`silentSinceUtc` равен `null`, `reportIntervalS` задан** — прибор на связи в пределах ожидаемого ритма.
- **`reportIntervalS` равен `null`** — у прибора нет объявленного ритма, сервер его на молчание не проверяет. Показывайте только возраст последнего контакта, без вывода «на связи / нет».

Решение «на связи / нет» принимает сервер, по своим часам. Не вычисляйте его в приложении по `lastSeenAtUtc`: порог может меняться настройками сервиса.

**Ошибки:** `404 device.not_found`, `400`, `429`, `503`.

## 7. Состояние устройства

```http
GET /api/mobile/devices/{deviceId}/state
```

Текущее состояние прибора — его **последний регулярный отчёт** (событие со статусом `100010`) — и то, как сервер видит его связь.

| Параметр | Где | Тип | Обязательный | Описание |
|---|---|---|---|---|
| `deviceId` | путь | integer | да | `id` устройства |

**Ответ `200 OK`:**

| Поле | Тип | Описание |
|---|---|---|
| `deviceId` | integer | id устройства |
| `lastSeenAtUtc` | string (date-time) или `null` | последний контакт по часам сервера |
| `reportIntervalS` | integer или `null` | период отчёта, объявленный прибором |
| `silentSinceUtc` | string (date-time) или `null` | см. [«Жив ли прибор»](#жив-ли-прибор) |
| `lastReport` | объект или `null` | последний отчёт `100010` по времени прибора; `null`, если отчётов не было |
| `lastReport.eventId` | string (UUID) | id события-отчёта |
| `lastReport.occurredAtUtc` | string (date-time) | время отчёта по часам прибора |
| `lastReport.receivedAtUtc` | string (date-time) | когда сервер его получил |
| `lastReport.payload` | объект или `null` | отчёт как есть; **значения и состояние каждого канала — в `payload.values`** |

```http
GET /api/mobile/devices/11/state
```
```json
{
  "deviceId": 11,
  "lastSeenAtUtc": "2026-10-19T12:22:11.692209Z",
  "reportIntervalS": 10,
  "silentSinceUtc": null,
  "lastReport": {
    "eventId": "01a1541c-bbec-7c1c-9d83-5b26125aa121",
    "occurredAtUtc": "2026-10-19T12:22:11.692209Z",
    "receivedAtUtc": "2026-10-19T12:22:11.692209Z",
    "payload": { "values": { "ch2": { "v": 4.4 } } }
  }
}
```

- **Показывайте только каналы, которые есть в `lastReport.payload.values`.** Набор каналов настраивается на приборе: снятый канал сам исчезает из отчёта. Не храните и не показывайте каналы из прошлых отчётов.
- Структура `payload.values` определяется прошивкой и не описана в API. Разбирайте её защищённо.
- Если `silentSinceUtc` задан, отчёт устарел: показывайте его как «последние известные значения» с датой.

**Ошибки:** `404 device.not_found`, `400`, `429`, `503`.

## 8. История событий устройства

```http
GET /api/mobile/devices/{deviceId}/events?limit={limit}&cursor={cursor}
```

События устройства, **новые сверху**: по `occurredAtUtc` по убыванию, при равном времени — по `id` по убыванию. История выдаётся страницами.

| Параметр | Где | Тип | Обязательный | Описание |
|---|---|---|---|---|
| `deviceId` | путь | integer | да | `id` устройства |
| `limit` | query | integer | нет | размер страницы, 1–100, по умолчанию 20 |
| `cursor` | query | string | нет | `nextCursor` из предыдущей страницы; для первой страницы не передаётся |

**Ответ `200 OK`:**

| Поле | Тип | Описание |
|---|---|---|
| `items` | массив событий | до `limit` событий; пустой, если событий нет |
| `nextCursor` | string или `null` | курсор следующей страницы; `null`, если страница последняя |
| `hasMore` | boolean | есть ли ещё события |

Событие:

| Поле | Тип | Описание |
|---|---|---|
| `id` | string (UUID) | id события; уникален, используйте как ключ в списке |
| `statusCode` | integer | код статуса, который прислало устройство (см. [раздел 10](#10-данные-событий)) |
| `occurredAtUtc` | string (date-time) | когда событие произошло по часам устройства; если устройство время не передало — время получения сервером |
| `receivedAtUtc` | string (date-time) | когда сервер принял событие |
| `payload` | объект или `null` | дополнительные данные от устройства, произвольный JSON-объект без фиксированной схемы |
| `source` | string | `device` — прислал прибор; `server` — создал сам сервер (`190001` «не выходит на связь», `190002` «снова на связи») |
| `channels` | массив `{id, name}` или `null` | каналы, к которым относится событие (например, `100003` «не отвечают каналы»); `name` может быть `null` |
| `occurredAtRejected` | boolean | `true` — время прибора было неправдоподобным (в будущем), и `occurredAtUtc` — это время получения сервером |

```http
GET /api/mobile/devices/1/events?limit=2
```
```json
{
  "items": [
    {
      "id": "01a1455b-94b5-70f3-aa9c-7a54c081237d",
      "statusCode": 200,
      "occurredAtUtc": "2026-10-16T10:05:00Z",
      "receivedAtUtc": "2026-10-16T15:36:32.18105Z",
      "payload": { "t": "10:05:00Z", "v": 3.3 },
      "source": "device",
      "channels": null,
      "occurredAtRejected": false
    },
    {
      "id": "01a1455b-9485-758a-8877-2392d5e71be6",
      "statusCode": 200,
      "occurredAtUtc": "2026-10-16T10:05:00Z",
      "receivedAtUtc": "2026-10-16T15:36:32.133399Z",
      "payload": null,
      "source": "server",
      "channels": null,
      "occurredAtRejected": false
    }
  ],
  "nextCursor": "CN8rbPBsbgABoUVblIV1ioh3I5LV5xvm",
  "hasMore": true
}
```

**Ошибки:** `404 device.not_found`, `400 pagination.invalid_limit`, `400 pagination.invalid_cursor`, `429`, `503`.

## 9. Пагинация истории

Пагинация курсорная: курсор указывает на последнее событие полученной страницы, следующая страница начинается сразу за ним.

**Бесконечная прокрутка вниз:**

1. Запросите первую страницу без `cursor`: `GET …/events?limit=20`.
2. Покажите `items`.
3. Если `hasMore = true`, при прокрутке к концу списка запросите `GET …/events?limit=20&cursor=<nextCursor>` и добавьте полученные `items` в конец.
4. Повторяйте, пока `hasMore = false` (`nextCursor` станет `null`).

**Правила:**

- **Курсор непрозрачен.** Не разбирайте его, не сохраняйте надолго и не конструируйте сами; передавайте ровно то значение, что пришло. Его формат может измениться.
- **Курсор привязан к устройству** и подходит только для того же `deviceId`.
- События с одинаковым временем не теряются и не повторяются на границах страниц.
- **Новые события не появляются в уже загруженных страницах**: курсор ведёт только «вглубь» истории. Чтобы увидеть новое (pull-to-refresh, возврат на экран), запросите первую страницу заново и замените список.
- Событие, которое устройство отправило с задержкой и временем из прошлого, встанет в историю на своё место по времени. При обновлении первой страницы оно может оказаться ниже уже загруженных событий, поэтому после refresh заменяйте список целиком, а не дописывайте.
- `limit` вне диапазона 1–100 даёт ошибку 400, сервер его не подрезает.
- Получили `400 pagination.invalid_cursor` — сбросьте список и загрузите первую страницу.
- Используйте `id` события как ключ элемента списка (diffing в SwiftUI, `DiffUtil` и т. п.).

## 10. Данные событий

- **`statusCode`** — число. Справочника кодов в API нет; известные коды:

  | Код | Значение |
  |---|---|
  | `100000` | прибор запущен |
  | `100001` | проверка связи (кнопка на приборе) |
  | `100003` / `100004` | не отвечают / снова отвечают каналы (`channels`) |
  | `100005` | перезапуск после сбоя (причина — `payload.reset`) |
  | `100006` / `100007` | запись на карту не идёт / восстановлена |
  | `100008` | файл настроек отвергнут, прибор на умолчаниях |
  | `100010` | регулярный отчёт (значения в `payload.values`) |
  | `190001` / `190002` | **серверные** события: прибор не выходит на связь / снова на связи |

  Устройства могут слать и другие коды. Показывайте неизвестный код как есть.
- **`payload`** — JSON-объект от устройства, до 8 КБ. Его структура зависит от модели устройства и не гарантирована: ключи могут отсутствовать или различаться. Разбирайте его защищённо и не завязывайте логику экрана на конкретные ключи без договорённости. Пример: `{"temperature": 25.4, "voltage": 3.3}`.
- **`occurredAtUtc` и `receivedAtUtc`.** Для пользователя показывайте `occurredAtUtc`. Часы устройства могут спешить или отставать. Если время прибора было в будущем больше чем на 5 минут, сервер подставил время получения и выставил `occurredAtRejected: true` — подпишите такое время как серверное. Большая разница между двумя временами означает, что устройство накопило события без связи и отправило их позже.

## 11. Генерация клиента

[`mobile-api.openapi.json`](mobile-api.openapi.json) — OpenAPI 3.1.1, проверен валидатором. Генерация, например, через [OpenAPI Generator](https://openapi-generator.tech):

```bash
# Swift (iOS)
openapi-generator generate -i docs/mobile-api.openapi.json -g swift5 -o ios/DeviceTelemetryApi

# Kotlin (Android)
openapi-generator generate -i docs/mobile-api.openapi.json -g kotlin -o android/devicetelemetry-api \
  --additional-properties=library=jvm-retrofit2,serializationLibrary=kotlinx_serialization
```

На что обратить внимание после генерации:

- `payload` описан как свободный объект (`object | null`, `additionalProperties`). Проверьте, что генератор отобразил его в словарь произвольных значений, например `[String: AnyCodable]` или `JsonObject`, а не в пустой тип.
- `channels` — массив объектов `TelemetryChannel` (`id`, `name`), может быть `null`.
- Проверьте разбор дат с разной длиной дробной части секунд (см. [раздел 2](#2-общие-соглашения)).
- Базовый URL задаётся переменной `baseUrl` в `servers` или настройкой клиента.

Файл генерируется из кода сервиса: после изменений API бэкенд-команда обновляет его командой `python scripts/export-mobile-openapi.py`. Рабочий сервис в окружении Development отдаёт полный документ по адресу `/openapi/v1.json`.

## 12. Что изменится

| Изменение | Влияние на клиент |
|---|---|
| Аутентификация пользователя (до production) | все запросы будут требовать заголовок авторизации; без него — `401`. Схема входа будет описана отдельно |
| Проверка владельца | чужой `customerId` или `deviceId` будут давать `403` или `404` |
| Привязка к пользователю | `customerId` в URL, вероятно, перестанет быть нужным: клиент будет определяться по токену |

Поля, добавленные в ответы, не считаются ломающим изменением (см. [раздел 2](#2-общие-соглашения)). Удаление или переименование полей и изменение смысла существующих полей будут объявлены заранее с новой версией контракта.

## 13. Данные для разработки (Staging)

На Staging при первом запуске создаются тестовые данные:

| Что | Значения |
|---|---|
| Клиенты | `customerId` от 1 до 10 |
| Устройства | по 5 у каждого клиента; их `id` берите из `GET /api/mobile/customers/{customerId}/devices` |
| События | появляются, когда устройства (или тестировщики) отправляют телеметрию; у новых устройств истории может не быть — это нормальный пустой результат |

Чтобы наполнить историю, попросите бэкенд-команду отправить тестовые события или используйте ключи устройств по инструкции в [DEPLOY.md](../DEPLOY.md) (раздел 2.6).
