# Протокол «устройство → сервер»

Как устройство отправляет телеметрию и как сервер её обрабатывает. Нужен, чтобы правки протокола не сломали уже работающие устройства. Описано поведение версии сервиса **1.3.0**; изменения относительно 1.2.0 совместимы (см. [раздел 7](#7-история-изменений)).

## 1. Транспорт

| | |
|---|---|
| Запрос | `POST /api/telemetry/send` — единственный endpoint, версии в пути нет |
| Тело | JSON, `Content-Type: application/json`; другой тип — `415` |
| Аутентификация | заголовок `X-Device-Key: dtk_…` (47 символов) — индивидуальный ключ устройства |
| Транспорт | HTTPS через reverse proxy; **временное исключение для HTTP** — см. [раздел 6](#6-временное-исключение-http-без-tls) |
| Лимиты | тело ≤ 32 КБ (`413`), `payload` ≤ 8 КБ, вложенность JSON ≤ 32, 600 запросов в минуту с одного IP (`429`) |

Ключ выдаётся командой `issue-device-key <deviceCode>`. В БД хранится только SHA-256 ключа; новая выдача отзывает старый ключ.

## 2. Сообщение

```json
{
  "deviceId": "stg-device-001",
  "statusCode": 100003,
  "messageId": "b5e15f27-3fb8-4e25-8c2f-f1a1b203b821",
  "occurredAtUtc": "2026-10-16T10:30:00Z",
  "payload": { "reset": "watchdog" },
  "channels": [ { "id": "ch2", "name": "130AA15P20" }, { "id": "ch5", "name": "130AA15P21" } ],
  "notifyEmail": "site-7@example.org",
  "reportIntervalS": 300
}
```

| Поле | Обяз. | Тип и ограничения | Смысл |
|---|---|---|---|
| `deviceId` | да | строка, 1–100 символов | внешний код устройства (`Device.DeviceCode`), **не** внутренний id |
| `statusCode` | да | целое int32, ≥ 0; **190000–199999 — `400`** (зарезервированы за сервером) | код события; смысл определяет устройство |
| `messageId` | нет | GUID, не нулевой | идентификатор сообщения для идемпотентности |
| `occurredAtUtc` | нет | ISO 8601 с `Z` или смещением; без зоны — `400`; раньше 2000-01-01 — `400` | время события по часам устройства; по умолчанию — время получения. **Позже «сейчас + 5 мин» — не ошибка** (см. ниже) |
| `payload` | нет | JSON-объект или `null`, ≤ 8 КБ в компактном виде | произвольные данные устройства, хранятся как `jsonb` |
| `channels` | нет (1.3) | массив ≤ 32 объектов `{"id": 1–16 символов, "name": ≤ 32 символа или нет}`; нарушение — `400` | каналы, к которым относится событие (`100003`, `100004`); хранятся в событии (`jsonb`) |
| `notifyEmail` | нет (1.3) | строка | адрес для уведомлений этого устройства. **Негодный адрес — не ошибка** (см. ниже) |
| `reportIntervalS` | нет (1.3) | целое, допустимо 10–86400 | период регулярного отчёта; включает контроль молчания. **Вне диапазона — не ошибка** (см. ниже) |

### Метаданные не отвергают сообщение

`400` для прибора окончателен: событие пропадает. Поэтому ошибки во **вспомогательных** полях не отвергают сообщение. Событие принимается, неверное значение игнорируется и сохраняется в событии для диагностики:

| Что пришло | Что делает сервер | Где видно |
|---|---|---|
| `occurredAtUtc` позже «сейчас + 5 мин» | время события = время получения | `TelemetryEvent.RejectedOccurredAtUtc`; в мобильном API `occurredAtRejected: true` |
| `notifyEmail` — не адрес, адрес с именем (`Имя <a@b>`), длиннее 254 символов | сохранённый адрес не меняется | `TelemetryEvent.RejectedNotifyEmail` |
| `reportIntervalS` вне 10–86400 | сохранённый интервал не меняется | `TelemetryEvent.RejectedReportIntervalS` |

Ошибки **типа** JSON — строка вместо числа, число вместо строки, не-массив в `channels` — по-прежнему дают `400`: тело в этом случае не разбирается.

### Поля, которые хранятся на устройстве

| Поле | Хранится в | Не передано или `null` | Пустая строка | Значение |
|---|---|---|---|---|
| `notifyEmail` | `Device.NotifyEmail` | не меняется | **снимает** адрес | заменяет адрес (пробелы по краям отбрасываются) |
| `reportIntervalS` | `Device.ReportIntervalS` | не меняется | — | заменяет интервал |

Получатель письма — `Device.NotifyEmail`, если он задан, иначе email клиента. Адрес из текущего сообщения действует уже для его собственного письма.

**Разбор JSON:**

- **Неизвестные поля молча игнорируются**: ошибки нет, данные теряются.
- **Регистр имён не важен:** `deviceId` = `DeviceId`.
- **Числа — только числами:** `"statusCode": "100001"`, `1.5` и значения больше int32 дают `400`.
- **При повторяющемся ключе побеждает последний.**
- **`payload` при хранении нормализуется:** `jsonb` меняет порядок ключей и пробелы, значения сохраняются.
- Смещение во времени (`+02:00`) приводится к UTC.

## 3. Ответы

| HTTP | Тело / `code` | Значение | Что делать устройству |
|---|---|---|---|
| `202` | `{eventId, receivedAtUtc, duplicate:false, notificationQueued}` | событие сохранено | готово |
| `200` | то же, `duplicate:true` | этот `messageId` уже принят с тем же содержимым | готово, не повторять |
| `400` | `telemetry.invalid` или `errors` без `code` | невалидное сообщение | не повторять, исправить сообщение |
| `401` | `device.authentication_failed` | неизвестное устройство **или** неверный ключ (ответ одинаковый намеренно) | не повторять, проверить ключ и `deviceId` |
| `409` | `telemetry.message_id_conflict` | `messageId` уже использован с другим содержимым | не повторять; ошибка генерации `messageId` |
| `413` | — | тело больше 32 КБ | уменьшить |
| `415` | — | не `application/json` | исправить заголовок |
| `429` | `rate_limit.exceeded`, заголовок `Retry-After` | превышен лимит | повторить через `Retry-After` |
| `503` | `service.unavailable`, `Retry-After: 30` | БД временно недоступна | повторить |
| `500` | — | ошибка сервера | повторить с нарастающей задержкой |

`notificationQueued: true` означает, что письмо поставлено в очередь, а не отправлено.

## 4. Обработка на сервере

1. Валидация контракта (Api), затем бизнес-валидация (`SendTelemetryCommandValidator`).
2. Поиск устройства по `deviceId` и проверка ключа.
3. Если есть `messageId`: поиск уже принятого сообщения этого устройства → `200` (содержимое совпадает) или `409` (не совпадает). Дальше повтор не идёт и состояние устройства не меняет.
4. В одной транзакции:
   - обновляются поля устройства: `LastSeenAtUtc` (время последнего контакта по серверным часам), `NotifyEmail`, `ReportIntervalS`;
   - если устройство было помечено молчащим — пометка снимается и создаётся серверное событие **`190002`**;
   - создаётся `TelemetryEvent`;
   - для каждого события с активным шаблоном письмо рендерится и пишется в Outbox.
5. Письма отправляет фоновый процесс.

Ошибки уведомления (нет шаблона, нет корректного адреса, ошибка в шаблоне) событие не отменяют.

### Серверные события и контроль молчания

Устройство не может сообщить о собственном отказе — это делает сервер. Раз в минуту (`SilenceMonitor:CheckInterval`) проверяются устройства с известным `ReportIntervalS`:

- **Молчит**, если от него нет никакого сообщения дольше `max(3 × ReportIntervalS, 10 мин)` по серверному времени получения. Тогда сервер создаёт событие **`190001` «прибор не выходит на связь»** и ставит `Device.SilentSinceUtc`. Событие создаётся одно на эпизод, а не на каждую проверку.
- **Первое сообщение после молчания** снимает пометку и создаёт **`190002` «прибор снова на связи»**, плюс обычное событие самого сообщения.
- **Устройство без `ReportIntervalS`** (старая прошивка, отчёт выключен) не контролируется: ожидаемого ритма нет.
- **Время берётся по серверным часам**: часы прибора на контроль не влияют.

Пометка и снятие — атомарные обновления строки устройства. Сообщение, пришедшее в момент проверки, не даст ложного `190001`; два параллельных сообщения не дадут двух `190002`; несколько экземпляров сервиса не дадут двух `190001`.

Серверные события — обычные `TelemetryEvent` с `Source = Server`, без `messageId`. Они идут через тот же Outbox и те же шаблоны. Порог и множитель настраиваются: `SilenceMonitor:ThresholdIntervals` (3), `SilenceMonitor:MinThreshold` (`00:10:00`).

### Какие события вызывают письмо

Письмо отправляется, если для `statusCode` есть активная строка в таблице `Templates`. Эталонный набор задан в коде (`DefaultTemplates`):

| Код | Тема письма | |
|---|---|---|
| `100000` | прибор запущен | старые прошивки шлют его и при возврате каналов |
| `100001` | проверка связи: сообщение получено | кнопка на приборе проверяет всю цепочку до ящика |
| `100003` | не отвечают каналы `{Channels}` | рендерится и без списка каналов |
| `100004` | снова отвечают каналы `{Channels}` | |
| `100005` | прибор перезапустился после сбоя | причина — в `payload.reset`, в письмо не выводится |
| `100006` / `100007` | запись на карту не идёт / восстановлена | |
| `100008` | файл настроек прибора отвергнут | прибор работает на умолчаниях |
| `100010` | **шаблона нет** | регулярный отчёт; письмо каждые несколько минут недопустимо |
| `190001` / `190002` | прибор не выходит на связь / снова на связи | серверные события |

Синтаксис шаблонов — `{Имя}`, двойные скобки `{{` `}}` — экранирование. Плейсхолдер списка каналов — **`{Channels}`** (`ch2 (130AA15P20), ch5 (130AA15P21)`); без списка он даёт пустую строку, остальные плейсхолдеры при пустом значении — ошибка рендера.

- **Staging** при каждом старте добавляет недостающие эталонные шаблоны и не трогает изменённые вручную.
- **Привести шаблоны к эталону** в любом окружении — командой `sync-templates` (`docker compose run --rm telemetry sync-templates`). Она перезаписывает шаблоны эталонных кодов, а остальные (например, `100002` из первой версии Staging) оставляет и перечисляет.

### Идемпотентность

- Уникальный индекс `(DeviceId, MessageId)` гарантирует одно событие на `messageId`, в том числе при параллельных повторах.
- Повтор считается тем же сообщением, если совпадает хеш содержимого — SHA-256 от:
  1. `statusCode`;
  2. момента `occurredAtUtc` в UTC, **если устройство его передало** — в том виде, как передано, даже если сервер его отверг;
  3. компактного JSON `payload` **в исходном порядке ключей**;
  4. **только если передан (1.3):** нормализованного списка `channels` в исходном порядке.
- `notifyEmail` и `reportIntervalS` в хеш **не входят**: это адресация и настройка, а не содержание события.
- Следствия:
  - хеш сообщения без `channels` такой же, как в 1.2.0, поэтому повторы событий, принятых до обновления, по-прежнему получают `200`;
  - другой порядок ключей в `payload` или другой порядок или состав `channels` дают `409`;
  - повтор, отличающийся только `notifyEmail`, `reportIntervalS` или неизвестными полями, — дубликат.
- Без `messageId` дубликаты не определяются: каждое сообщение — новое событие.

**Рекомендация устройству:** генерировать `messageId` один раз на сообщение, хранить до получения `200`/`202` и повторять при таймауте, `429`, `5xx` **с тем же `messageId` и тем же телом**.

## 5. Как расширять протокол

### Куда класть новые данные

- **В `payload`**, если сервер их только хранит и показывает (показания датчиков, версия прошивки, диагностика). Серверных правок не нужно.
- **Отдельным полем верхнего уровня**, только если сервер должен их понимать: валидировать, хранить на устройстве, индексировать, подставлять в письма, учитывать в идемпотентности.

### Совместимые и ломающие изменения

| Изменение | Совместимость |
|---|---|
| Новое **необязательное** поле | совместимо в обе стороны: старый сервер его проигнорирует (данные потеряются), новый примет старые устройства |
| Новые ключи в `payload` | совместимо |
| Новый `statusCode` | совместимо; письмо — через строку в `Templates`, эталон — в `DefaultTemplates` |
| Ослабление ограничения (раньше `400`, теперь принимается) | совместимо |
| Новое **обязательное** поле, переименование, смена типа или смысла поля, ужесточение ограничений | **ломает** уже выпущенные устройства |

Порядок раскатки совместимого поля: **сначала сервер, потом прошивки**. Ломающее изменение — через новый endpoint (`POST /api/v2/telemetry/send`), старый оставить, пока работают старые прошивки.

**Решение по каждому новому полю:**
- **Ошибка в значении:** если поле вспомогательное, неверное значение не отвергает сообщение, а сохраняется в событии (`Rejected…`).
- **Хеш:** если поле должно отличать «другое сообщение» от «повтора», добавляйте его в `ComputeContentHash` только когда оно передано. Тогда хеши старых прошивок не меняются.
- **Хранение:** на устройстве (состояние) или в событии (содержание).

### Что править в коде (новое поле верхнего уровня)

| Слой | Файл | Что сделать |
|---|---|---|
| Api | `Contracts/SendTelemetryRequest.cs`, `Controllers/TelemetryController.cs` | поле (nullable), перенос в команду |
| Application | `SendTelemetryCommand.cs`, `SendTelemetryCommandValidator.cs` | поле команды; бизнес-ограничения (только для содержимого) |
| Application | `SendTelemetryCommandHandler.cs` | запись в событие или устройство; решение по хешу |
| Domain / Infrastructure | `TelemetryEvent.cs` / `Device.cs`, конфигурации EF, новая миграция | колонка nullable без значения по умолчанию |
| Уведомления | `EmailTemplateRenderer.cs`, `NotificationContext`, `DefaultTemplates.cs` | плейсхолдер в явный список (и в `OptionalPlaceholders`, если данных может не быть) |
| Мобильный API | `Mobile/Queries/*`, `docs/mobile-api.*` | поле в DTO, повторная выгрузка OpenAPI |
| Тесты | `IntegrationTests/SendTelemetryCommandHandlerTests.cs` | старое сообщение без поля по-прежнему принимается, хеш прежний; повтор с полем и без — по выбранной семантике |
| Документация | этот файл, `README.md`, `DeviceTelemetry.Api.http` | |

## 6. Временное исключение: HTTP без TLS

**Статус:** действует. **Срок:** до **2027-04-19** (предложение; подтвердите или назначьте свой срок — дата должна совпасть с планом выпуска прошивки с TLS). **Ответственный за снятие:** команда прошивки.

Приборы пока не умеют TLS. До выхода прошивки с клиентским TLS reverse proxy принимает **plain HTTP только для `POST /api/telemetry/send`**. Всё остальное — мобильный API и любые другие пути — только по HTTPS.

**Риск.** Ключ устройства и тело сообщения передаются открыто. Кто перехватит трафик, сможет:
- отправлять ложную телеметрию от имени прибора;
- с версии 1.3 — подменить `notifyEmail` и **перенаправить тревожные письма заказчика на свой адрес**;
- отправкой `reportIntervalS` включить или исказить контроль молчания.

**Меры на период исключения:**
- приборы и сервер — в сети, где перехват маловероятен (VPN/APN оператора), если это возможно;
- при подозрении на утечку — перевыпуск ключа (`issue-device-key`);
- рекомендуется доработка: при смене `Device.NotifyEmail` отправлять уведомление на прежний адрес и адрес клиента. В 1.3.0 этого **нет**.

**Пример конфигурации nginx** (не проверялся на этом проекте):

```nginx
server {                                   # HTTP: только приём телеметрии
    listen 80;
    server_name telemetry.example.com;

    location = /api/telemetry/send {
        limit_except POST { deny all; }
        proxy_pass http://telemetry:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    location / { return 403; }             # без редиректа: клиент не должен повторять запрос с ключом
}

server {                                   # HTTPS: всё
    listen 443 ssl;
    server_name telemetry.example.com;
    ssl_certificate     /etc/ssl/telemetry/fullchain.pem;
    ssl_certificate_key /etc/ssl/telemetry/privkey.pem;

    location / {
        proxy_pass http://telemetry:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

**До включения прокси:** сервис пока не обрабатывает `X-Forwarded-For`. За прокси все клиенты будут для него одним IP — адресом прокси, и лимит 600 запросов в минуту (120 для мобильного API) станет общим на всех. Нужна настройка forwarded headers с доверенной сетью прокси. Её нет в 1.3.0. Порт 8080 сервиса после включения прокси наружу публиковать нельзя.

**Снятие исключения:** после выпуска прошивки с TLS на всех приборах закрыть `listen 80` для `/api/telemetry/send` и удалить этот раздел.

| Версия | Изменения |
|---|---|
| 1.3.0 | необязательные поля `notifyEmail`, `channels`, `reportIntervalS`; контроль молчания и серверные события `190001`/`190002`; диапазон `19xxxx` зарезервирован (`400`); `occurredAtUtc` из будущего принимается с временем получения; плейсхолдер `{Channels}`; эталонные шаблоны и `sync-templates` |

## 8. Известные ограничения

- Неизвестные поля и опечатки в именах не вызывают ошибок.
- Нет версии протокола и способа сообщить устройству о новой версии.
- Нет пакетной отправки: одно сообщение — один HTTP-запрос. Для устройства, накопившего события без связи, это много запросов и быстрый выход за rate limit.
- Лимит запросов считается по IP: устройства за одним NAT делят его, а за прокси без forwarded headers — все клиенты делят один.
- `occurredAtUtc` раньше 2000-01-01 по-прежнему даёт `400`. По той же логике, что и для времени из будущего, его можно было бы принимать с временем получения — в 1.3.0 не сделано.
