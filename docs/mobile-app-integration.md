# Задание для мобильного приложения: работа с сервером DeviceTelemetry

Документ — постановка для разработчика мобильного приложения (или ИИ-ассистента, который его пишет): что приложение показывает, откуда берёт данные и где легко ошибиться. Совместимо с сервером **1.6.0** (контракт мобильного API **1.3.0**).

- Справочник по полям, ошибкам и пагинации — [mobile-api.md](mobile-api.md).
- Машиночитаемая спецификация для генерации клиента — [mobile-api.openapi.json](mobile-api.openapi.json).
- Как приборы общаются с сервером (для понимания данных) — [device-protocol.md](device-protocol.md).

## 1. Что это за система

Приборы (регистраторы, датчики) отправляют на сервер события и регулярные отчёты. Сервер хранит историю, следит, не пропал ли прибор со связи, и рассылает письма заказчику. Приложение **только читает** эти данные: настройки приборов из приложения пока не меняются (см. раздел 8).

Объекты:

- **Клиент** (`customerId`) — заказчик, у которого есть приборы.
- **Устройство** (`id`) — прибор клиента. Внешний код `deviceCode` (например, `stg-device-001`) можно показывать как серийный номер, но в запросах используется только числовой `id`.
- **Событие** — сообщение прибора или сервера: код статуса, время, данные (`payload`).

## 2. Подключение

| | |
|---|---|
| Базовый URL (Staging) | `http://<адрес VPS>:8080` — вынести в конфигурацию сборки |
| Префикс | `/api/mobile` |
| Аутентификация | **нет** (временно, MVP) — см. раздел 9 |
| Формат | JSON, UTF-8, `GET`; живые значения — WebSocket |

- Staging работает по **HTTP**: для отладочных сборок нужно исключение — ATS на iOS (`NSExceptionDomains`), `network_security_config.xml` на Android. В релизную сборку исключение не включать.
- Лимит — **120 запросов в минуту с одного IP**. При превышении приходит `429` с заголовком `Retry-After`. Пользователи за одним NAT делят лимит: не опрашивайте сервер чаще, чем нужно экрану.

## 3. Экраны и запросы

| Экран | Запрос | Что показать |
|---|---|---|
| Список приборов клиента | `GET /api/mobile/customers/{customerId}/devices` | имя, код, **возраст последнего контакта**, отметка «не на связи» |
| Карточка прибора | `GET /api/mobile/devices/{id}` | имя, последнее событие, связь, часовой пояс, каналы |
| Текущее состояние | `GET /api/mobile/devices/{id}/state` | значения каналов из последнего регулярного отчёта |
| История событий | `GET /api/mobile/devices/{id}/events?limit=20&cursor=…` | лента событий, новые сверху, бесконечная прокрутка |
| Live (если `features` содержит `live`) | WebSocket `GET /api/mobile/devices/{id}/live` | значения каналов в реальном времени |
| Данные (если `features` содержит `history`) | `GET …/logs?ch=N[&month=YYYY-MM]`, `GET …/data/{path}` | файлы данных прибора по каналам и дням |

### 3.1. Список приборов

```json
[ { "id": 1, "deviceCode": "stg-device-001", "name": "DataLoggerSTM32",
    "lastSeenAtUtc": "2026-10-19T13:03:22.184939Z", "silentSinceUtc": null } ]
```

- **Главное поле — `lastSeenAtUtc`**: когда сервер в последний раз получил что-либо от прибора, по часам сервера. Показывайте возраст относительно часов телефона: «2 мин назад», «3 ч назад».
- **`silentSinceUtc` не `null`** — прибор **не выходит на связь**. Выделите это в списке (цвет, иконка).
- `lastSeenAtUtc: null` — прибор ещё ни разу не выходил на связь.
- Список не пагинируется и отсортирован по имени, при равных именах — по `id`.

### 3.2. Карточка прибора

Пример (часовой пояс, порог и каналы появляются, когда прибор передаёт их командой настроек):

```json
{ "id": 1, "deviceCode": "stg-device-001", "name": "DataLoggerSTM32", "customerId": 1,
  "lastEventAtUtc": "2026-10-19T13:03:22Z", "lastStatusCode": 100010,
  "lastSeenAtUtc": "2026-10-19T13:03:22.184939Z", "reportIntervalS": 300, "silentSinceUtc": null,
  "offlineAfterS": 1800, "monitoring": true, "timeZone": "Europe/Berlin",
  "channels": [ { "id": "ch1", "name": "130AA15P20" }, { "id": "ch2", "name": "TEX0000001" } ],
  "features": [] }
```

**Статус связи** — строго по правилам ниже. Решение принимает сервер по своим часам; не вычисляйте его в приложении по `lastSeenAtUtc`.

| Условие | Показать |
|---|---|
| `silentSinceUtc` не `null` | «Не выходит на связь с …» (дата из `lastSeenAtUtc`) |
| `monitoring: false` | «Плановое отключение» — контроль связи выключен прибором |
| `reportIntervalS` или `offlineAfterS` задан, `silentSinceUtc: null` | «На связи» |
| оба `null` | только возраст последнего контакта, без вывода «на связи / нет» |

- `lastEventAtUtc` / `lastStatusCode` — **последнее событие любого типа**, а не текущее состояние. Подписывайте как «последнее событие».
- `channels` — справочник имён каналов, заданный прибором. Используйте его, чтобы подписать каналы в истории, если у события канал пришёл без имени.
- **`features`** — какие дополнительные экраны показать: `live` и/или `history` (разделы 3.6 и 3.7). Поле есть всегда. Пустой массив — обычный случай: прибор без Device Link или функция выключена на сервере (в production — до появления авторизации). Не показывайте кнопки этих экранов, если значения нет; неизвестные значения пропускайте.

### 3.3. Текущее состояние

```json
{ "deviceId": 1, "lastSeenAtUtc": "…", "reportIntervalS": 300, "silentSinceUtc": null,
  "lastReport": { "eventId": "…", "occurredAtUtc": "…", "receivedAtUtc": "…",
    "payload": { "fw": "FW 2.96", "card": "ok", "clock": "rtc", "bootId": 929, "uptimeS": 2161,
                 "values": [ { "id": "ch1", "name": "130AA15P20", "v": 3655.000, "unit": "um", "s": "ok" },
                             { "id": "ch2", "name": "TEX0000001", "v": 24.577, "unit": "degC", "s": "ok" } ] } } }
```

- **`payload.values` — массив**, по элементу на канал: `id` — канал, `name` — имя датчика, `v` — значение, `unit` — единица измерения, `s` — состояние канала. Это формат прошивки FW 2.96. API его не фиксирует, поэтому разбирайте защищённо, а неизвестные ключи и значения `s` показывайте как есть.
- **Показывайте только каналы, которые есть в последнем отчёте.** Снятый с прибора канал сам исчезает из отчёта: не храните и не показывайте каналы из старых отчётов.
- `lastReport: null` — регулярных отчётов ещё не было; покажите пустое состояние.
- Если прибор не на связи (`silentSinceUtc`), подпишите значения как «последние известные» с датой.
- Остальные ключи `payload` — сведения о приборе (версия прошивки, карта памяти, время работы). Их можно вывести в разделе «О приборе».
- Обновлять экран: при открытии и по pull-to-refresh. Автообновление — не чаще `reportIntervalS` (новых данных раньше всё равно не будет).

### 3.4. История событий

```json
{ "items": [ { "id": "01a15442-…", "statusCode": 100002, "occurredAtUtc": "…", "receivedAtUtc": "…",
               "payload": { "battery": { "v": 3.31, "pct": 12, "thresholdPct": 15 } },
               "source": "device", "channels": null, "occurredAtRejected": false } ],
  "nextCursor": "CN8t3pfBvZoBoVQwVYJ3qK4j32XUBf-s", "hasMore": true }
```

- **Пагинация курсорная.** Первая страница — без `cursor`; пока `hasMore = true`, передавайте полученный `nextCursor` **без изменений**. Курсор непрозрачный: не разбирайте его и не храните.
- **Обновление (pull-to-refresh)** — заново запросить первую страницу и **заменить** список целиком. Курсор ведёт только вглубь истории, новых событий в нём нет.
- **Ключ элемента списка** — `id` события (для diffing в SwiftUI, `DiffUtil` и т. п.).
- **`source: "server"`** — событие создал сервер (`190001`–`190003`). Отличайте его визуально от событий прибора.
- **`occurredAtRejected: true`** — часы прибора были неверны, и `occurredAtUtc` — это время сервера. Подпишите время как серверное.
- **`channels`** — каналы события (`100003`/`100004`). Если `name` нет, возьмите имя из справочника карточки (`channels`).
- `limit` — от 1 до 100. Значение вне диапазона даёт `400`, сервер его не подрезает.

### 3.5. Коды событий

| Код | Подпись | Данные |
|---|---|---|
| `100000` | Прибор запущен | |
| `100001` | Проверка связи | |
| `100002` | **Низкий заряд батареи** | `payload.battery`: `v` (В), `pct` (%), `thresholdPct` (порог) — если прошивка передаёт |
| `100003` / `100004` | Не отвечают / снова отвечают каналы | `channels` |
| `100005` | Перезапуск после сбоя | причина — `payload.reset` |
| `100006` / `100007` | Запись на карту остановлена / восстановлена | |
| `100008` | Файл настроек отвергнут, работа на умолчаниях | |
| `100010` | Регулярный отчёт | `payload.values` (раздел 3.3) |
| `190001` | **Сервер:** прибор не выходит на связь | `payload.lastSeenAtUtc`, `thresholdS` |
| `190002` | **Сервер:** прибор снова на связи | `payload.silentSinceUtc` |
| `190003` | **Сервер:** изменён адрес уведомлений | без адресов (по соображениям приватности) |

- **Неизвестный код** показывайте как «Событие {код}». Приборы могут присылать новые коды раньше, чем обновится приложение.
- **Регулярные отчёты `100010`** приходят каждые несколько минут и быстро заполняют ленту. Предусмотрите фильтр «скрыть регулярные отчёты» — на клиенте, сервер такого фильтра не даёт.

### 3.6. Live

WebSocket `ws://…/api/mobile/devices/{id}/live` (`wss://` в production). Сервер шлёт кадры `{"type":"status","state":…}` и `{"type":"values",…}`, клиент ничего не отправляет. Подробно — [mobile-api.md, раздел 11](mobile-api.md#11-живые-значения-websocket).

- Статусы: `connecting` → «Подключение…», `streaming` → значения, `device_offline` → «Прибор не в сети» (соединение не закрывать: прибор вернётся сам), `not_supported` → сообщение; сервер закроет соединение, переподключаться не нужно.
- **Live — это не отчёт.** Подпишите экран и значения как **«Live · Server»**: это поток, который сервер транслирует от прибора прямо сейчас, со временем сервера `receivedAtUtc`. Значения регулярного отчёта (раздел 3.3) — другое: это запись прибора с его временем. Не смешивайте их на одном графике без подписи.
- Пропуски значений — норма: медленному клиенту сервер отдаёт только последние кадры.
- Открывайте соединение, только пока экран на виду; при обрыве переподключайтесь с нарастающей задержкой. Ошибки до соединения: `404 feature.not_available`, `429` — повторить через `Retry-After`.

### 3.7. Данные прибора

Копии файлов данных прибора на сервере; доступны и когда прибор не в сети. Подробно — [mobile-api.md, раздел 12](mobile-api.md#12-сохранённые-данные).

1. Каналы: `0` — сводный файл, далее номера каналов (`ch1` → `1`).
2. `GET …/logs?ch=1` → `{"months":[…]}`, затем `GET …/logs?ch=1&month=2026-10` → `{"days":[{"path","size","complete"}]}`.
3. `GET …/data/{path}`: `path` кодируется целиком, вместе с `/` (`ch1%2F2026-10%2F23.TSV`). Ответ — байты как есть: табуляция, десятичная запятая, CRLF, строки `#` — заголовок, `-99999,50` — нет значения. Последнюю неполную строку незакрытого дня отбросьте.
4. `complete: true` — файл больше не изменится, кешируйте навсегда. Незакрытый день догружайте хвостом: `Range: bytes=<скачано>-` с `If-Range: <ETag>`; `200` вместо `206` значит, что файл перечитан, — замените копию.
5. `503 sync.pending` — файл копируется с прибора: «Загрузка с прибора…», повтор через `Retry-After`. `503 device.offline` — копии нет, а прибор не в сети.

## 4. Время

- Все времена в ответах — UTC в ISO 8601 с `Z`. **Дробная часть секунд необязательна и бывает разной длины — от 0 до 7 знаков** (`…13:03:22Z`, `…13:03:22.184939Z`). Парсер должен принимать все варианты. На iOS `ISO8601DateFormatter` строг к наличию дробной части: делайте две попытки разбора. На Android `Instant.parse()` справляется сам.
- **По умолчанию показывайте время в часовом поясе телефона.**
- **Время прибора** при необходимости: в карточке есть `timeZone` — IANA-имя (`Europe/Berlin`) или смещение (`+02:00`); `null` — пояс не задан.
- `occurredAtUtc` — время события по часам прибора, `receivedAtUtc` — время получения сервером. Пользователю показывайте `occurredAtUtc`. Большая разница между ними означает, что прибор накопил события без связи и отправил позже.

## 5. Ошибки

Формат — RFC 9457 Problem Details (`application/problem+json`) со стабильным полем `code`. Реакцию стройте на HTTP-статусе и `code`, а не на тексте `detail`.

| HTTP / `code` | Действие |
|---|---|
| `404 customer.not_found` / `device.not_found` | «Не найдено»; для устройства — закрыть экран и обновить список |
| `400 pagination.invalid_cursor` | сбросить историю, загрузить первую страницу |
| `400` (`invalid_limit` или `errors` без `code`) | ошибка в коде приложения — в лог/краш-репорт |
| `429 rate_limit.exceeded` | повторить через `Retry-After` секунд |
| `503 service.unavailable` | повторить через `Retry-After` |
| `500`, таймаут, нет сети | повтор с нарастающей паузой, затем экран ошибки с кнопкой «Повторить» |

Все запросы — `GET`, повторять их безопасно. В отчёты об ошибках включайте `traceId` из ответа: по нему сервер найдёт запрос в логах.

## 6. Генерация клиента

```bash
openapi-generator generate -i docs/mobile-api.openapi.json -g swift5 -o ios/DeviceTelemetryApi
openapi-generator generate -i docs/mobile-api.openapi.json -g kotlin -o android/devicetelemetry-api \
  --additional-properties=library=jvm-retrofit2,serializationLibrary=kotlinx_serialization
```

После генерации проверьте:
- `payload` — свободный объект: ожидается `[String: AnyCodable]` / `JsonObject`, а не пустой тип;
- разбор дат с разной длиной дробной части секунд;
- что неизвестные поля в ответах **игнорируются** — сервер может добавлять новые поля, и это не считается ломающим изменением.

## 7. Данные для разработки (Staging)

- **Клиенты** — `customerId` 1–10, по 5 приборов у каждого; `id` приборов берите из списка клиента.
- **`customerId = 1`, прибор `id = 1` (`DataLoggerSTM32`)** — **настоящий прибор** с живыми данными: регулярный отчёт каждые 5 минут, два канала. Лучший источник для отладки экранов состояния и истории.
- У остальных тестовых приборов истории может не быть — это нормальный пустой результат.

## 8. Чего в API пока нет

- **Изменение настроек прибора** (адрес и язык уведомлений, порог отключения, имена каналов) — сейчас их задаёт только прибор. Позже приложение тоже сможет их менять по правилу «последняя запись выигрывает». Не делайте экраны редактирования до появления API.
- **Адрес уведомлений прибора** в ответах не отдаётся намеренно: API без авторизации.
- **Push-уведомления** — нет; тревоги приходят заказчику письмом.
- **Фильтры истории** по коду или периоду на сервере — нет.

## 9. Ограничения MVP

- **Авторизации нет:** любой, кто знает адрес сервера, может прочитать данные любого клиента, перебирая `customerId`. **Не публикуйте приложение в сторах с этой версией API.**
- До production будет добавлен вход пользователя. Тогда запросы потребуют заголовок авторизации, чужие данные начнут давать `403`/`404`, а `customerId` в URL, вероятно, станет не нужен. Заложите в сетевом слое место для токена.
- Контракт расширяется только добавлением полей. Удаление и переименование полей будут объявлены заранее с новой версией.

## 10. Проверка перед сдачей

- [ ] Список клиента 1: у `DataLoggerSTM32` возраст контакта — минуты, нет отметки «не на связи».
- [ ] Прибор без событий открывается без ошибок: пустая история, `lastReport: null`.
- [ ] Состояние показывает оба канала из `payload.values` с единицами измерения.
- [ ] Прокрутка истории до конца без пропусков и повторов; pull-to-refresh заменяет список.
- [ ] Событие `100002` подписано «Низкий заряд батареи», заряд показан, если есть `payload.battery`.
- [ ] Серверные события (`source: "server"`) визуально отличаются от событий прибора.
- [ ] Неизвестный код события не ломает экран.
- [ ] Даты разбираются и без дробной части секунд, и с ней.
- [ ] Отключение сети и ошибки `429`/`503` дают понятное состояние и повтор, а не падение.
- [ ] В релизной сборке нет исключения для HTTP.
- [ ] При пустом `features` кнопок Live и «Данные» нет, экран прибора работает как раньше.
- [ ] Live: на экране подпись «Live · Server»; при выключении прибора — «Прибор не в сети», после включения поток возобновляется без перезахода на экран.
- [ ] Данные: файл незакрытого дня догружается хвостом (`206`), байты совпадают с полной загрузкой; `503 sync.pending` даёт повтор, а не ошибку.
