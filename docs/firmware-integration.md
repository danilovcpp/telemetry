# Задание для прошивки: обмен с сервером DeviceTelemetry

Документ — постановка для разработчика прошивки прибора (или ИИ-ассистента, который её пишет). Здесь всё, что прибор должен отправлять на сервер и как обрабатывать ответы. Совместимо с сервером **1.5.0** и выше. Полный протокол с правилами сервера — [device-protocol.md](device-protocol.md).

## 1. Транспорт и общие правила

- **Адрес:** `http://<сервер>:<порт>` — задаётся в настройках прибора. HTTPS прибор пока не поддерживает: на сервере действует временное исключение для двух путей ниже.
- **Запросы:** только `POST`, тело — JSON в UTF-8, заголовки:
  ```
  Content-Type: application/json
  X-Device-Key: dtk_…        ← ключ прибора, 47 символов; хранить в защищённой области, в логи не выводить
  ```
- **Имена полей** — как в примерах (camelCase). Числа отправлять числами (`300`, не `"300"`), иначе сервер ответит `400`.
- **Неизвестные поля сервер молча игнорирует.** Опечатка в имени поля не даст ошибки — данные просто пропадут. Проверяйте имена по этому документу.
- **`deviceId`** — код прибора (например, `stg-device-001`), выдаётся вместе с ключом.
- **Размеры:** тело ≤ 32 КБ, `payload` ≤ 8 КБ.

## 2. Время

- Отправляйте время события `occurredAtUtc` в ISO 8601 **с указанием пояса**: `2026-10-19T13:03:22Z` или по местным часам со смещением `2026-10-19T15:03:22+02:00`. Время без пояса (`2026-10-19T13:03:22`) сервер отвергнет с `400`.
- Если часы не установлены (после сброса RTC), **не отправляйте `occurredAtUtc` вовсе**: сервер подставит время получения. Время раньше 2000 года даёт `400`.
- Время больше чем на 5 минут в будущем сервер заменит временем получения (событие не теряется).
- Часовой пояс прибора сообщите сервером командой настроек (`timeZone`, раздел 4): в письмах будет строка «время прибора» в этом поясе.

## 3. Сообщение о событии — `POST /api/telemetry/send`

```json
{
  "deviceId": "stg-device-001",
  "statusCode": 100010,
  "messageId": "6f1c2a4e-0b7d-4c55-9a1e-3d2f8b9c0a11",
  "occurredAtUtc": "2026-10-19T15:03:22+02:00",
  "payload": { "values": [ { "id": "ch1", "name": "130AA15P20", "v": 3655.0, "unit": "um", "s": "ok" } ] }
}
```

| Поле | Обяз. | Что передавать |
|---|---|---|
| `deviceId` | да | код прибора |
| `statusCode` | да | код события (таблица ниже). **190000–199999 не использовать** — зарезервированы за сервером (`400`) |
| `messageId` | рекомендуется | случайный UUID v4, **новый для каждого события** (см. «Повторы») |
| `occurredAtUtc` | нет | время события (раздел 2) |
| `payload` | нет | JSON-объект с данными события, ≤ 8 КБ |
| `channels` | для 100003/100004 | `[{"id":"ch2","name":"130AA15P20"}]` — каналы, к которым относится событие; `name` можно не передавать, если имена переданы командой настроек |

### Коды событий

| Код | Когда отправлять | Письмо |
|---|---|---|
| `100000` | после включения/перезагрузки | «прибор запущен» |
| `100001` | нажата кнопка проверки связи | «проверка связи: сообщение получено» |
| `100002` | **низкий заряд батареи** (раздел 5) | «низкий заряд батареи» |
| `100003` / `100004` | каналы перестали / снова начали отвечать, со списком `channels` | да |
| `100005` | перезапуск после сбоя; причина — в `payload.reset` | да |
| `100006` / `100007` | запись на карту остановилась / восстановилась | да |
| `100008` | файл настроек отвергнут, работа на умолчаниях | да |
| `100010` | регулярный отчёт с `payload.values` (каждые `reportIntervalS` секунд) | нет |

### Ответы и что делать прибору

| HTTP | Значение | Действие |
|---|---|---|
| `202` | событие принято | удалить из очереди отправки |
| `200` с `"duplicate": true` | это событие уже было принято раньше (повтор) | удалить из очереди |
| `400` | неверное сообщение | **не повторять**; записать в журнал прибора, удалить из очереди |
| `401` | неверный ключ или `deviceId` | не повторять; показать ошибку настройки связи |
| `409` | `messageId` уже использован с другим содержимым | не повторять; ошибка генерации `messageId` |
| `413` | тело слишком большое | уменьшить `payload` |
| `429` | слишком часто | повторить через `Retry-After` секунд |
| `503`, `500`, таймаут, нет сети | временная проблема | повторить с нарастающей паузой: 10 с, 30 с, 1 мин, 5 мин… |

### Повторы

- **Без потерь:** держите очередь неотправленных событий (лучше в энергонезависимой памяти) и удаляйте событие только после `202` или `200`.
- **Без дубликатов:** при повторе отправляйте **тот же `messageId` и байт-в-байт то же тело**. Тогда сервер ответит `200 duplicate`, а не создаст второе событие и не пришлёт второе письмо. Порядок ключей в `payload` и `channels` при повторе менять нельзя: это даст `409`.
- **Без `messageId`** каждый повтор станет новым событием, а для тревог — новым письмом.

## 4. Настройки прибора — `POST /api/telemetry/settings`

Отправлять **после включения** (сразу после `100000`) и **сразу после любого изменения настроек** на приборе. Повторная отправка тех же значений безопасна.

```json
{
  "deviceId": "stg-device-001",
  "name": "DataLoggerSTM32",
  "notifyEmail": "site-7@example.org",
  "notifyLanguage": "ru",
  "timeZone": "Europe/Berlin",
  "reportIntervalS": 300,
  "offlineAfterS": 1800,
  "monitoring": true,
  "channels": [
    { "id": "ch1", "name": "130AA15P20" },
    { "id": "ch2", "name": "TEX0000001" }
  ]
}
```

| Поле | Значение | Ограничения | Пустая строка / `[]` |
|---|---|---|---|
| `name` | имя прибора в письмах и в мобильном приложении | 1–200 символов | нельзя (будет отвергнуто) |
| `notifyEmail` | куда слать уведомления этого прибора | e-mail без имени (`a@b.ru`, не `Имя <a@b.ru>`) | письма уходят на адрес клиента |
| `notifyLanguage` | язык писем | `en`, `ru`, `de` | язык клиента, иначе английский |
| `timeZone` | часовой пояс прибора | IANA (`Europe/Berlin`, лучше: учитывает летнее время) или смещение (`+02:00`) | UTC |
| `reportIntervalS` | период отчёта `100010` | 10–86 400 с | — |
| `offlineAfterS` | через сколько секунд без сообщений считать прибор отключённым | 600–604 800 с (10 мин – 7 дней) | — |
| `monitoring` | `false` — плановое отключение: сервер не шлёт «не выходит на связь» | `true` / `false` | — |
| `channels` | справочник каналов: имена подставляются в письма | ≤ 32, уникальные `id` (≤ 16), `name` ≤ 32 | очищает справочник |

- **Отсутствующее поле не меняется на сервере.** Передавайте только то, что прибор знает.
- **Последняя запись выигрывает.** Позже настройки сможет менять и мобильное приложение; прибор при следующей отправке перезапишет их своими значениями.
- Без `offlineAfterS` сервер считает прибор отключённым через `max(3 × reportIntervalS, 10 минут)`.
- Перед плановым выключением прибора (транспортировка, обслуживание) отправьте `"monitoring": false`, после включения — `"monitoring": true`.
- **Смена `notifyEmail`** — сервер отправит письмо на **прежний** адрес: «уведомления теперь уходят на …». Это защита от тихой подмены адреса.

### Ответ — показать пользователю

```json
{
  "settings": { "name": "DataLoggerSTM32", "notifyEmail": "site-7@example.org", "notifyLanguage": "ru",
                "timeZone": "Europe/Berlin", "reportIntervalS": 300, "offlineAfterS": 1800, "monitoring": true,
                "channels": [ { "id": "ch1", "name": "130AA15P20" } ] },
  "rejected": { "notifyEmail": "not a valid email address" }
}
```

- `200` — команда выполнена. `settings` — что **сейчас хранит сервер**, `rejected` — поля, которые сервер не принял, с причиной. Отвергнутое поле на сервере не изменилось.
- **Если `rejected` не пуст — покажите это на экране прибора**, например «Адрес почты не принят сервером». Иначе пользователь будет уверен, что настройка применилась.
- `400` — только при ошибке формата JSON (строка вместо числа и т. п.); `401` — неверный ключ; `429`/`5xx` — повторить позже, как в разделе 3.

## 5. Низкий заряд батареи — `100002`

Сервер на `100002` отправляет письмо «низкий заряд батареи» на адрес прибора (или клиента) на выбранном языке. Ниже — как прибору правильно его формировать.

**Когда отправлять:**
- **Один раз на эпизод.** Отправьте `100002`, когда заряд **опустился ниже порога** (например, 15 % или напряжение ниже 3,4 В — порог в настройках прибора). Пока заряд остаётся низким, повторно не отправляйте: каждое сообщение — отдельное письмо заказчику.
- **Гистерезис.** Новый эпизод начинается только после того, как заряд **поднялся выше порога с запасом** (например, порог + 10 %) или батарея заменена/заряжена. Иначе колебания напряжения около порога дадут поток писем.
- **Напоминание** — не чаще одного раза в 24 часа, если заряд всё ещё низкий (по желанию; это тоже письмо).
- **Состояние эпизода** («уже сообщил») храните в энергонезависимой памяти, чтобы перезагрузка не вызвала повторное письмо.
- **Если связи нет**, событие ставится в очередь и уходит при восстановлении связи. `occurredAtUtc` — момент, когда заряд упал ниже порога, а не момент отправки.

**Сообщение:**

```json
{
  "deviceId": "stg-device-001",
  "statusCode": 100002,
  "messageId": "0d6f1a52-7a1e-4c1d-9f61-2b7c0e5a9a10",
  "occurredAtUtc": "2026-10-19T15:10:00+02:00",
  "payload": { "battery": { "v": 3.31, "pct": 12, "thresholdPct": 15 } }
}
```

- `payload.battery` — фактическое напряжение (`v`, вольты), процент (`pct`) и порог (`thresholdPct`). Сервер сохраняет их в событии, мобильное приложение видит их в истории.
- **В письмо уровень заряда сейчас не попадает:** шаблоны не выводят поля `payload`. Если цифры нужны в письме, это доработка сервера (новый плейсхолдер).
- **Отдельного кода «заряд восстановлен» нет.** Если он нужен, его нужно согласовать и добавить на сервере (шаблон письма), а не придумывать в прошивке.
- Заряд стоит дублировать в регулярном отчёте `100010` (`payload.battery`): так мобильное приложение показывает текущий заряд, а не только момент тревоги.

**Ответ:** `202` — принято, письмо поставлено в очередь (`"notificationQueued": true`). Для прошивки это то же, что для любого события (раздел 3).

## 6. Последовательность после включения

1. Отправить `100000` («прибор запущен»).
2. Отправить `POST /api/telemetry/settings` со всеми настройками; показать `rejected`, если он не пуст.
3. Отправить накопленные в очереди события (с их исходными `messageId`).
4. Дальше — `100010` каждые `reportIntervalS` секунд и события по мере возникновения.

## 7. Проверка перед выпуском прошивки

- [ ] Кнопка проверки связи (`100001`) → письмо приходит на `notifyEmail` на выбранном языке, в письме верное «время прибора».
- [ ] Неверный адрес в настройках → на экране прибора сообщение из `rejected`.
- [ ] Смена `notifyEmail` → письмо о смене приходит на **прежний** адрес.
- [ ] Обрыв связи на время больше `offlineAfterS` → письмо «не выходит на связь»; после восстановления — «снова на связи».
- [ ] `monitoring: false`, затем выключение на сутки → писем о молчании нет.
- [ ] Повтор отправки после таймаута → `200 duplicate`, второго письма нет.
- [ ] Заряд ниже порога → одно письмо `100002`; колебания около порога и перезагрузка — без повторных писем.
- [ ] Каналы `100003` без имён в сообщении → в письме имена из справочника `channels`.
- [ ] В журнале прибора нет ключа `X-Device-Key`.
